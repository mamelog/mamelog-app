# ドキュメント品質の黄金原則

mamelog-app リポジトリのすべてのドキュメントが満たすべき品質基準。

## 6つの原則

### 1. 読者第一 (Reader First)

読者が必要な情報に最短でたどり着ける構造にする。

- タイトルと冒頭で「何についてのドキュメントか」が分かる
- 結論・推奨を先に書き、詳細は後に展開する
- 専門用語には初出時に説明を付ける

### 2. 構造化 (Structured)

機械的に検証可能な一貫したフォーマットを使う。

- frontmatter（title, date, status）を docs/ 配下のファイルに付与する
- Markdown の見出しレベルを正しく使う（H1 はタイトルのみ、H2 以降でセクション分け）

### 3. リンク (Linked)

孤立したドキュメントを作らない。

- 関連するドキュメントへの相互リンクを張る
- 設計ドキュメントは docs/ 内の相対リンクで参照する
- 内部リンクは相対パスで記述する

### 4. 鮮度 (Fresh)

陳腐化したドキュメントは積極的に更新またはアーカイブする。

- docs/ は 180日が鮮度の閾値
- status フィールドで現在の状態を明示する（draft / review / approved / outdated）
- 情報が古くなった場合は `status: outdated` に更新する

### 5. 検証可能 (Verifiable)

人間の判断に頼らず、機械的に検証できるルールを優先する。

- frontmatter の存在と必須フィールドはリンターが検証する
- 内部リンクの死活はリンターが検証する
- ファイル名の kebab-case はリンターが検証する

### 6. 最小限 (Minimal)

重複を避け、Single Source of Truth を維持する。

- 同じ情報を複数箇所に書かない。リンクで参照する
- ツールバージョンは mise.toml を唯一の情報源とする

## status フィールドの定義

| 値         | 意味                 | 次のアクション               |
| ---------- | -------------------- | ---------------------------- |
| `draft`    | 作成中。内容が不完全 | レビューを受けて review へ   |
| `review`   | レビュー中           | 承認されたら approved へ     |
| `approved` | 承認済み。現在有効   | 定期的に鮮度をチェック       |
| `outdated` | 内容が古くなった     | 更新するか、アーカイブを検討 |
